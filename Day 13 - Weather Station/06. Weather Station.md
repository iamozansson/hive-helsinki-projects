# WeatherStation

Optimize payload sizes for incoming weather station telemetry.

## The Situation

You're working on a custom server which accepts incoming data from weather stations. You're building the part of the system which transforms incoming messages from weather stations into a format which can be used by other parts of the system.

Those weather stations send their meteorological data every minute, but they only send the data that has changed in the last 60 seconds to keep message payloads as small as possible. Luckily, those weather stations send a full snapshot every 10 minutes, so there shouldn't be too many gaps in the data if the odd message goes missing.

Your infrastructure is considered as critical national infrastructure, and your senior architect has instructed you not to use any fancy tools for remembering the previous state of the weather station.

You decide to tackle this problem head on with nothing but raw code.

## Functional Requirements

Your objective is to implement a component that can remember each weather station's previous state, so that you can broadcast its full known state when a partial update message arrives. You decide to make a test to deal with a single weather station, before scaling your solution to deal with all weather stations.

### Overview

Your program will:

1. **Read** lines from standard input until `exit` is entered.
2. **Parse** each line as one of:

   * **Data update:** `<id>,<value>`
   * **Query:** `get`
   * **Reset:** `clear`
   * **Termination:** `exit`
3. **Maintain** an internal state of nine meteorological sensors.
4. **Print** the full state on `get`.

No menus or prompts should be printed—each line of input triggers exactly one action.

## Program Initialisation

When your program starts, it should print:

```text
--- Weather Station ---
```

## Data Points

Weather stations send their data as comma separated value strings, and each data point has a numerical code.

You can use the following table to link data point IDs with their internal strings:

| ID | Key             |
| -- | --------------- |
| 1  | `airTemp`       |
| 2  | `airPressure`   |
| 7  | `precipitation` |
| 11 | `windSpeed`     |
| 12 | `windDirection` |
| 13 | `humidity`      |
| 14 | `dewPoint`      |
| 15 | `soilMoisture`  |
| 22 | `cloudCover`    |

The values are formatted as floats.

The initial state is that all data points are `NULL`.

## Messages

Messages are received as CSV strings.

For example:

```text
11,15.5
13,32.3
```

There are occasions where there is no data to report for a given sensor. In these cases, `NULL` values will be sent:

```text
11,0
12,NULL
```

The inputs will always be valid. The CSV string will never be malformed. The first column will always be a positive integer. The second column will always be a float or `NULL`.

If no data has changed, no message will be sent.

## Return State

The state is always reported in full, ordered by ID.

If no state is known about a data point, `NULL` is displayed.

```text
airTemp:21.6
airPressure:31.0
precipitation:0.4
windSpeed:0.0
windDirection:NULL
humidity:9.1
dewPoint:12.3
soilMoisture:33.2
cloudCover:1008.0
```

## Technical Implementation

Your program must read commands from standard input (`stdin`) and write responses to standard output (`stdout`).

No menus or prompts should be printed—each line of input triggers exactly one action.

When your program starts, it should print:

```text
--- Weather Station ---
```

### `id,value`

Updates a sensor value.

Example:

```text
11,15.5
```

sets `windSpeed` to `15.5`.

Example:

```text
12,NULL
```

sets `windDirection` to missing.

Invalid lines or IDs outside the table are ignored.

### `get`

Prints all sensor values, one per line, in ascending ID order.

### `clear`

Resets all fields back to missing values (`NULL` when printed).

### `exit`

Prints:

```text
Exiting...
```

and exits the program.

## Project Structure

`main.go` needs to be located at the **root** of your `weatherStation` repository.

This is the entry point of the application, maintaining the weather station state and processing input commands.

If you use packages, your Go module name should match your repository name:

```text
weatherStation
```

While the location of `main.go` is a strict requirement, you're free to implement the program's internal logic in any way you choose, as long as it produces the expected standard output (`stdout`).
